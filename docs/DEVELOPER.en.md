## 2. Where to change what

### 2.1 Look & feel (colors / fonts / breakpoints)

Everything lives in the CSS variables at the top of `site/wrt/app.css`; change once, applies site-wide:
`--bg/--card/--card2` (backgrounds), `--text/--text2/--text3` (text), `--accent*` (brand blue), `--danger/--warn/--ok/--gold` (status), `--radius/--shadow`.
Dark mode is defined **twice** (`html[data-theme="dark"]` for manual and `@media (prefers-color-scheme: dark)` for auto) — edit both.
Type scale: 17px body (15.5px compact via the Aa toggle); 15px pills/plugin cells/group headers; 14px hints. Breakpoints: 860px / 560px / 400px; plugin grid `repeat(auto-fill, minmax(150px,1fr))` (126px compact).

### 2.2 UI strings & i18n

- Chinese source: `tools/i18n-source.json` (the only hand-edited entry point; keep `{x}` placeholders intact)
- Other 10 languages: `tools/i18n-translations.json` (including Traditional Chinese)
- Then run `node tools/gen-i18n.mjs` → emits `site/wrt/data/i18n.json` + `docs-private/翻译对照表.md`
- Validation: all 11 UI languages must be complete; `check-all` rejects any missing entry
- `i18n.json` is network-first and uses localStorage only as an offline fallback, preventing a newly deployed key from being hidden by a stale table for the current page. When a `data-i18n` key is absent, keep the human-readable HTML fallback instead of exposing an internal key.

### 2.3 Plugins

- Curated display metadata: `tools/plugins-meta.json` (name/group/desc/size/hot/locked/warn/per-source `pkgs` mapping/`exclude`). It controls shortcuts and presentation only; dependencies, reverse dependencies, choices, selects, implies, conflicts, and providers come exclusively from the weekly Catalog.
- For 360T7, capacity estimates prefer the median compressed dependency-closure size in `tools/plugin-sizes.json`; missing entries fall back to the hand estimate in `plugins-meta.json`. This snapshot is MT7981-specific, so seed devices always keep hand estimates.
- Group order = the `groups` array order (the proxy group currently sits last)
- Run `node tools/gen-plugins.mjs` afterwards. It warns about packages present in configs but missing from metadata. `data/<device>/packages.json` is still generated for the package reference page and schema-3/4 legacy request compatibility, but the customizer no longer exposes a duplicate raw-package editor.
- Curated names and descriptions live in `tools/plugins-i18n.json`. All ten translated languages, including independent Traditional Chinese, must provide both fields for all 226 plugins; technical package names and `CONFIG_PACKAGE_*` symbols remain unchanged.
- Chinese-only display masking lives in `site/wrt/app.js`: `ZH_SUB` (euphemism replacement) and `EN_MASK` (star masking)

### 2.4 Devices

- Registry: `site/wrt/data/devices.json` (used only by CI, generators, and legacy-request compatibility; the page no longer loads it. Only 360T7 is fully maintained; all other devices are seed configs.)
- Public web data under `site/wrt/data/` must not contain `.config` files. Authoritative base configs live only under `config/`; `gen-plugins.mjs` removes old public copies and generates plugin/package indexes.
- Device catalog: `tools/device-catalog.json`, rebuilt by parsing real `TARGET_DEVICES` and `Device/*` inheritance per branch; `node tools/gen-seed-configs.mjs` then creates an independent minimal config for every source/branch/profile.
- Target controls and plugin options remain schema-driven. `site/wrt/lib/catalog-engine.js` is the only relation calculator; `applyCatalogIntent()` in `app.js` only submits user intent and synchronizes UI state. Enabling an item recursively adds uniquely determined mandatory dependencies and `select` targets. Disabling a dependency recursively disables invalid dependents. Disabling a plugin prunes auto-added dependencies only when no enabled consumer remains and no baseline, recommended, imported, or explicit user layer protects them. Shared and explicitly selected dependencies survive. `imply`, multiple providers, and deferred conditions are left to upstream Kconfig. Plugin-name, translation-package, and theme-link exceptions are forbidden in `app.js`.
- Importing `.config`, JSON, or `config.buildinfo` waits for the matching Catalog before restoring Target/menuconfig state. The page no longer runs a global `proposeRepairs()` pass or silently rewrites imported input. Catalogued symbols continue through the shared interaction engine; truly unknown symbols stay in the import workspace, and the complete uploaded config remains authoritative.
- JSON import starts with strict `JSON.parse`. A legacy WeiG schema 3–6 file may be recovered only when the embedded `config` string has unescaped `.config` quotes and the document also carries the WeiG generated header, `pageVersion`, and `use_defconfig`. Recovery uses fixed field boundaries, never `eval`, and asks the user to export a standards-compliant JSON afterward.
- The Target locator and Current build contract share one outer card and equal 42px headers. Expanded contract content spans both columns and renders paired Source/Branch, Target/Subtarget, Profile/Packages, and Catalog/Architecture fields. Interactive package changes never dump whole-config violations into a toast; direct package/choice conflicts use a themed N/M/Y switch dialog. The Recommended configuration button keeps its position and is disabled, not hidden, while Recommended is off.
- Upstream `.packageinfo` and Kconfig English remain authoritative. Advanced search indexes only package/option names and localized names, never symbols, paths, usage, or long help. Each row shows an ID without `CONFIG_PACKAGE_` on the left, a right-aligned one-line locale/English description in the middle, and fixed N/M/Y controls on the right. Hover, focus, or tap on the ID/description shows the full `CONFIG_*` symbol, locale text, upstream English, and menu path without Chinese/English/Index/Path labels, and the popup may not cover N/M/Y.
- Catalog schema 6 splits each branch into `core`, `graph`, `menu`, `hidden`, `help`, and current-language menu assets. Initial branch selection fetches only `core + graph`; opening Advanced fetches the visible menu and current locale, the first search adds hidden display metadata, and clicking a truncated full description fetches long Help. `graph` uses compact relations schema 3, while the schema-5 monolith remains only as a migration fallback. Every state mutation increments a revision; Target context, expression tokens, visibility, and maximum N/M/Y level are reused within that revision. A Worker builds the search index once, input is debounced by 180 ms, and the main thread receives symbol IDs only. Long Help is excluded from default search, and rendering remains bounded to 80 rows per scroll page instead of constructing the full Catalog DOM.
- Every ordinary Advanced item can open the unified detail popup whether or not visible text is clipped. English also gets the full CONFIG symbol, English description, and path; other locales add their real translation. Source/Branch loading, exact Catalog commit/hash/bytes validation, schema-6 assets, and the no-Catalog-on-VPS deployment contract are unchanged.
- Desktop uses hover/focus and mobile taps the ID or description; N/M/Y taps only change state. Popup width is constrained by the left edge of the row actions. Category, choice, paging, search Worker, and responsive behavior retain the existing performance design.
- The browser accepts Catalog data only when schema, commit, compressed byte count, and SHA-256 match the index. New build-request schema 5 records the Catalog repository, immutable data revision, legacy asset/hash/bytes, Catalog/relations schemas, upstream repository, and upstream source commit. The Issue parser reads only the fixed index and compares that version contract field by field; it no longer downloads the monolith to scan the complete `.config`. The Workflow builds the exact upstream commit, while schemas 3/4 remain legacy-only. `Top level` remains the root breadcrumb, and curated Applications are browser-Catalog-driven UI shortcuts.
- Catalog Publish validates each branch independently. A valid branch immediately replaces its rolling shard; a failed or corrupt branch is quarantined and keeps the `catalog-data` last-good result, with the index reporting fresh/stale/unavailable. Partial runs still update rolling data while the failed matrix keeps the workflow red. The complete Release updates only when every branch succeeds and validates.
- Catalog translation uses the workflow's minimal `models: read` permission and processes up to 500 changed texts per weekly run by default. Translation warnings go to `translation-summary.json` and the Publish Summary; manual tables, upstream English, and successfully generated catalogs remain publishable when the model is unavailable.
- Minimal 360T7 configs do not carry the full Kconfig package table. `tools/package-baseline-360t7.json` preserves the complete three-source Developer-search snapshot and `gen-plugins` merges it into `packages.json`.
- Never delete comments inside config files — both the frontend and CI only do line replacement

### 2.5 Build pipeline

- For a Catalog Target, `arch`, `archPackages`, Target, and Profile identity remain one atomic build contract. Profile-declared packages move to a compact manager: Follow upstream writes nothing, while explicit Include or Exclude writes `y` or `n`. The submitted config is generically checked only before optional Defconfig. A successful upstream `make defconfig` is not subject to project-specific post-validation. `tools/apply-config-overrides.mjs`, `tools/config-overrides.mjs`, and `system-overrides.json` are removed, so the workflow no longer forces `CONFIG_DEVEL` or `CONFIG_BUILD_LOG`.

- Catalog state keeps baseline, recommended, explicit user, automatic dependency, and imported origin layers. `catalogDependencySymbols` tracks only engine-added values. After disabling a plugin, the engine may prune entries no longer required by any enabled item, while baseline, recommended, imported, and non-`n` explicit user state protect dependencies. Profile package decisions use a sparse `profilePackageOverrides` map that stores only explicit Include/Exclude changes.

- `.github/workflows/custom-build.yml` accepts only web-generated Issue attachments; `repository_dispatch` and the hidden smoke configuration generator are removed. Issue titles use `[build] request-stamp/build-tag/Target/Source/Branch/Profile`, and the parser normalizes `build_ref` to `request-stamp-build-tag`. Every upstream `.img.gz` becomes its own unwrapped Artifact with that prefix and the original filename; supporting groups become `request-stamp-build-tag-CONFIG`, `BUILD-LOGS`, `OPTIONAL-PACKAGES`, and `FIRMWARE-OTHER`. Timezone, theme, NTP, and opkg are cross-checked in the submitted config, Summary, `firmware-settings.txt`, and the firmware's `/etc/weig-build-info`. Firmware/config live 30 days; complete logs live 14 days.
- Package-source mirrors are handled automatically by `diy2-generic.sh`: legacy opkg sources rewrite `distfeeds.conf`; APK sources (25.12+) rewrite the build-time `VERSION_REPO`, from which the source generates `distfeeds.list`. With `Asia/Shanghai`, the page selects the first Mainland China mirror available for the current Source unless the user has explicitly chosen a mirror; Source changes revalidate that choice. `check-all` combines the device registry and Catalog index and requires every active Source (ImmortalWrt, OpenWrt, lede, and hanwckf) to expose at least one Mainland China mirror. hanwckf reuses the USTC/PKU ImmortalWrt mirror paths. Do not treat the generated APK file as a fixed source-tree file.
- Build admission defaults to at most two queued or running builds per requester; a third Issue is commented on and closed. The repository owner is identified from the GitHub login, bypasses that limit, and receives a per-run concurrency group so owner builds do not queue behind one another. A fork can override the positive-integer default through the repository Variable `MAX_BUILDS_PER_USER`. `cancel-build.yml` accepts `/cancel` or `/cancel-build` only from the originating Issue author, tries normal cancellation first, and force-cancels only if it remains active after 15 seconds. Administrators can still manage any run in Actions.
- Root `VERSION` is the shared repository/web minute-level `vYYMMDDHHmm` source; `site-version.json` is its static-deployment copy. Actions records VERSION, the request page version, customizer commit, upstream commit, and all inputs.
- Download and parallel compilation use dynamic concurrency and retain complete logs. A failed parallel compile retries with `make -j1 V=s BUILD_LOG=1`, requesting upstream per-package logs without changing `.config`. The Catalog engine is now browser-interaction-only: it applies mandatory dependencies, `select`, choice, reverse invalidation, and orphan cleanup. The backend no longer judges whole-config package relations and the manual `config-rules` layer is removed. Optional official `make defconfig` is the only backend configuration resolver; otherwise the submitted config is used directly.
- `config/001.presets/source-build-requirements.json` now carries only the frontend compatibility marker `CONFIG_HAVE_DOT_CONFIG=y`, silently added when Defconfig is disabled; `site/wrt/data/source-build-requirements.json` is the static web copy. The backend does not load this rule and does not reject a request when it is absent. If every build later runs Defconfig unconditionally, this frontend compatibility layer can be removed.
- For schema 5, the parser reads only the fixed Catalog index and verifies the requested revision/legacy metadata plus `sourceCommit`; it no longer downloads the Catalog monolith or scans the complete `.config`. The backend keeps request-safety allowlists and minimal Target/Profile identity only, with no ARCH/ARCH_PACKAGES, package-relation, manual compatibility, theme-package, or build-requirement rejection.
- All versioned base configs disable PassWall/SSR Plus/VSSR/TinyProxy and their proxy engines/sub-options by default. `check-all.mjs` fails if any default config contains a proxy `CONFIG_PACKAGE_*=y/m`. Config preflight writes proxy-related symbols selected in the actual pre-build config to `proxy-selected.txt` and the Summary; an explicit user selection may still add its normal dependencies.
- `tools/parse-request.mjs`: full whitelist validation, including device/source/version/variant, packages, login settings, timezone, theme, NTP and opkg. The beginner Issue exposes one required attachment field and recommends the web JSON. The parser still accepts 1–3 GitHub-hosted JSON/`.config`/`config.buildinfo` attachments, but a raw config without web metadata must be loaded on the page first.
- Issue attachments are the only build entry: frontend `applyToConfig()` → complete `build-request.json` → `submitted.config` → `openwrt/.config`. The old `build-config.mjs`, `repository_dispatch`, and smoke compatibility entry are removed.
- `site/wrt/data/timezones.json` carries the 445-entry OpenWrt LuCI timezone table. With an empty search, the combobox shows about 70 common cities ordered by the current offset from `UTC-12` to `UTC+14`; typing searches all 445 entries. `Beijing` and its Chinese aliases are search-only aliases for `Asia/Shanghai`. On a first visit with no saved choice or imported configuration, the browser-reported IANA timezone is selected; a manual choice is stored locally. The page submits an IANA `zonename`; the parser maps it to the POSIX `timezone`, and all three diy2 scripts write both through `files/etc/uci-defaults/10-weig-timezone`. The control remains 44px high and legacy POSIX values remain accepted.
- The workflow-level `TZ` controls process timestamps only. Do not call `timedatectl set-timezone` on a GitHub-hosted runner: systemd may deny it and fail the dependency-install step. Firmware timezone handling is independent and remains request/diy2 driven.
- `sync-upstream.yml` (weekly, off-peak) refreshes the catalog/seeds and auto-commits; `check-drift.mjs` checks only the shared OpenWrt branch policy and opens an issue on drift; `mirror-upstream.yml` (monthly, needs `secrets.MIRROR_TOKEN`) mirrors upstreams. Build regression tests use real web-generated Issue requests rather than a smoke dispatcher.
- `site-version.yml` watches `site/wrt/**` and `VERSION`, updates root `VERSION` and `site-version.json` together by content fingerprint, then bot-commits them once. Parsers still accept legacy `vYYMMDDHH` requests. Desktop shows the version immediately left of Load configuration, while screens at 560px or below keep it in the right-aligned footer. The actor condition prevents commit loops.

#### Removing builtins with direct-config builds

- In Developer mode, `-id` writes the matching `CONFIG_PACKAGE_*` as an explicit `# ... is not set`; the complete config is used directly unless the request explicitly enables one upstream Defconfig pass. Its output is no longer subjected to a project-specific before/after target-identity comparison.
- `CONFIG_DEFAULT_*` supplies a default value, not a mandatory `select`; it may coexist with an explicit disabled state for the matching `CONFIG_PACKAGE_*`.
- The upstream build system may still resolve symbols selected through Kconfig dependencies; that is distinct from this project explicitly running `make defconfig`. System-baseline entries marked `locked` cannot be removed in the UI.
- Check dependencies and risk warnings before removing a builtin; an explicit disable does not mean the package can never be restored as a dependency.

### 2.7 Deploy & migrate

- Copy the whole `site/wrt/` folder anywhere. Catalog data uses exact cache → latest GitHub Raw index → pinned-commit jsDelivr/GitHub Raw shard → complete GitHub Release; the VPS stores no Catalog, while other static data keeps relative paths and local-first fallback. `OpenWebPage_打开网页.bat` keeps only one visible `wrt-server` window; closing it stops the local preview.
- Browser dynamic imports are fixed at `lib/catalog-engine.js`, `lib/catalog-loader.js`, and `lib/catalog-schema6.js`; Advanced search uses `lib/catalog-search-worker.js`. The `.js` suffix reuses the JavaScript MIME mapping already present on ordinary static servers; `lib/package.json` with `type: module` exists only for Node/CI imports. Legacy `.mjs` files must be removed. The deploy script validates all four scripts before packaging, after remote extraction, and through a live HTTP MIME/body smoke test after the switch; a missing file, HTML fallback, or non-JavaScript MIME restores the previous site. Archive manifests are checked only by `tools/verify-site-archive.mjs`, which invokes `tar` with `shell: false` and validates all required/forbidden entries in one pass. BAT-level `tar | findstr` pipelines are forbidden, so Unicode/space paths and nested CMD parsing cannot rewrite the command arguments.
- After a fork, edit only `site/wrt/data/project.json` for the main repository, Catalog repository, and blog URL. Runtime links, Issue targets, and Catalog loading follow that file; literal HTML links remain old-deployment fallbacks.
- Blog mirror: `node tools/sync-blog.mjs [blog path]` exact-mirrors the whole `site/wrt/` tree into blog `source/wrt/`, including `.config` files and empty directories. It does not use `fs.cpSync()`; one generic tree walker creates directories, copies files individually, and verifies staging content with chunked SHA-256 before the atomic swap. Unicode/space paths and large binary files use the same path-independent logic. The CLI reports copy progress, failures preserve or restore the previous mirror, and `--check` returns 0 for an exact tree or 3 when synchronization is needed.
- Text-format gate: `node tools/check-text-format.mjs <repository path> --changed` checks only current Git changes and untracked text files. It enforces LF for source/data files, CRLF for BAT/CMD/PowerShell, UTF-8 without BOM, and exactly one final newline according to `.gitattributes`; it reports errors but never rewrites files. The main-repository actions in `Sync_Deploy.bat` run this gate before the full `check-all` and `git diff --check`. Git messages saying CRLF will later be replaced by LF are informational warnings; the actual blocking error is printed separately.

### 2.8 Cloud-build testing guide (manual Run workflow)

**Version and variant must belong to the selected source** — mismatches are rejected instantly by `parse-request.mjs` (the error lists the legal options; just re-run with them):

| source | versions | variants | notes |
|---|---|---|---|
| `ImmortalWrt` | every upstream remote branch | profiles that exist in that branch | old branches without the device are hidden |
| `OpenWrt` | `main` + every `openwrt-*` branch | profiles that exist in that branch | excludes `lede-17.01`, `pcs-standalone-back`, and `master` |
| `lede` | `master` | profiles that exist in that branch | append mode; plugin availability depends on lede feeds |

GitHub's Run-workflow form cannot cascade dropdowns, hence the manual pairing; **the web page never has this problem** (it only offers legal versions/variants per source).

**Recommended test order** after a fresh push or big change: ① use the page to select a currently fresh stable ImmortalWrt branch, a common Target, and `ttyd`; ② verify Advanced hidden-symbol search and a dependency-removal cascade; ③ submit through the Issue path and confirm the pinned Catalog/source commit in Summary; ④ manual `sync-upstream`; ⑤ submit real Issue requests for the other source/Target combinations; ⑥ then alternate profiles, imported unknown symbols, custom `lanip`, and `@empty`.

**Reading failures**: instant red = parameter validation, so read the `parse-request` step output. Download and compile steps stream raw output live while also writing complete files; if GitHub truncates a long console log, use the `BUILD-LOGS-…` artifact. For compile-stage red, read in order: `00-SUMMARY.txt` → `build-metadata.txt` → `build-diagnostic.log` (if present) → full `download.log` / `build.log` → `errors.txt` / `tail-200.txt` → `package-logs.tar.gz` (if present) → `final.config`. Common causes: `Package xxx is missing`, out-of-space, or a temporary upstream breakage.

**Second-level local checks without waiting for CI**: run `node tools/parse-request.mjs` with `REQUEST_FILE` or `REQUEST_MANIFEST` pointing to a web-generated attachment, then run `node tools/check-all.mjs` (including every versioned base config in the proxy-default scan).

**Facts**: a build takes ~2–3h uncached; ~20 parallel jobs on the free tier; independent original `.img.gz`, `CONFIG`, `OPTIONAL-PACKAGES`, and `FIRMWARE-OTHER` live 30 days while `BUILD-LOGS` lives 14 days; use a dated tag (e.g. `weige-0727`) to tell batches apart; cancelled issue-builds are commented and closed by the bot too.

## D100: Catalog Schema 6 vs. the Actions build contract

Every Catalog branch index must explicitly contain:

```json
{
  "assets": { "core": {}, "graph": {} },
  "legacy": {
    "asset": "source--branch.json.gz",
    "hash": "<compressed sha256>",
    "bytes": 123,
    "catalogSchema": 5,
    "relationsSchema": 2
  }
}
```

`assets` serves the browser's Schema 6 / Relations 3 runtime. `legacy` serves the exact Schema 5 / Relations 2 asset validated by Actions. Contract changes must be reviewed together in `site/wrt/app.js`, `site/wrt/lib/catalog-loader.js`, and `tools/parse-request.mjs`. Never combine `branch.asset/hash/bytes` with schemas taken from the in-memory `MENU_CATALOG`. A branch without an explicit `legacy` contract may still be browsed, but cloud-build submission must be blocked.

On Windows, run the Catalog checks with:

```powershell
npm.cmd test
```
