## 2. Where to change what

### 2.1 Look & feel (colors / fonts / breakpoints)

Everything lives in the CSS variables at the top of `site/wrt/app.css`; change once, applies site-wide:
`--bg/--card/--card2` (backgrounds), `--text/--text2/--text3` (text), `--accent*` (brand blue), `--danger/--warn/--ok/--gold` (status), `--radius/--shadow`.
Dark mode is defined **twice** (`html[data-theme="dark"]` for manual and `@media (prefers-color-scheme: dark)` for auto) — edit both.
Type scale: 17px body (15.5px compact via the Aa toggle); 15px pills/plugin cells/group headers; 14px hints. Breakpoints: 860px / 560px / 400px; plugin grid `repeat(auto-fill, minmax(150px,1fr))` (126px compact).

### 2.2 UI strings & i18n

- Chinese source: `tools/i18n-source.json` (the only hand-edited entry point; keep `{x}` placeholders intact)
- Other 10 languages: `tools/i18n-translations.json` (including Traditional Chinese)
- Then run `node tools/gen-i18n.mjs` → emits `site/wrt/data/i18n.json` + `docs-private/翻译对照表.md`
- Validation: all 11 UI languages must be complete; `check-all` rejects any missing entry
- `i18n.json` is network-first and uses localStorage only as an offline fallback, preventing a newly deployed key from being hidden by a stale table for the current page. When a `data-i18n` key is absent, keep the human-readable HTML fallback instead of exposing an internal key.

### 2.3 Plugins

- Curated display metadata: `tools/plugins-meta.json` (name/group/desc/size/hot/locked/warn/per-source `pkgs` mapping/`exclude`). It controls shortcuts and presentation only; dependencies, reverse dependencies, choices, selects, implies, conflicts, and providers come exclusively from the weekly Catalog.
- For 360T7, capacity estimates prefer the median compressed dependency-closure size in `tools/plugin-sizes.json`; missing entries fall back to the hand estimate in `plugins-meta.json`. This snapshot is MT7981-specific, so seed devices always keep hand estimates.
- Group order = the `groups` array order (the proxy group currently sits last)
- Run `node tools/gen-plugins.mjs` afterwards. It warns about packages present in configs but missing from metadata. `data/<device>/packages.json` is still generated for the package reference page and schema-3/4 legacy request compatibility, but the customizer no longer exposes a duplicate raw-package editor.
- Curated names and descriptions live in `tools/plugins-i18n.json`. All ten translated languages, including independent Traditional Chinese, must provide both fields for all 226 plugins; technical package names and `CONFIG_PACKAGE_*` symbols remain unchanged.
- Chinese-only display masking lives in `site/wrt/app.js`: `ZH_SUB` (euphemism replacement) and `EN_MASK` (star masking)

### 2.4 Devices

- Registry: `site/wrt/data/devices.json` (used only by CI, generators, and legacy-request compatibility; the page no longer loads it. Only 360T7 is fully maintained; all other devices are seed configs.)
- Public web data under `site/wrt/data/` must not contain `.config` files. Authoritative base configs live only under `config/`; `gen-plugins.mjs` removes old public copies and generates plugin/package indexes.
- Device catalog: `tools/device-catalog.json`, rebuilt by parsing real `TARGET_DEVICES` and `Device/*` inheritance per branch; `node tools/gen-seed-configs.mjs` then creates an independent minimal config for every source/branch/profile.
- Target controls remain schema-driven. The normal menu uses visible Kconfig options only, while Advanced search also indexes hidden Kconfig and packageinfo-only records. Generated entries such as `luci-i18n-*` can therefore be found, inspected, and removed from imported residue, but hidden records cannot be force-enabled outside their controlling dependencies. `site/wrt/lib/catalog-engine.js` is the only standard relation interpreter: enabling an item adds only uniquely determined mandatory dependencies; disabling an item follows reverse indexes, re-evaluates complete expressions, and recursively disables only truly invalid dependents. `app.js` must not contain plugin names, translation-package prefixes, or theme dependency exceptions. Existing menu navigation, batching, breadcrumbs, and responsive behavior remain UI concerns.
- Importing `.config`, JSON, or `config.buildinfo` waits for the matching Catalog before restoring Target/menuconfig state. The shared engine then produces a repair preview so invalid hidden residue and broken dependency chains do not survive silently into Actions; line-level edits are applied only after confirmation. An uncatalogued Target remains an explicit `custom-target`, and truly unknown symbols stay in the paged import workspace.
- Upstream `.packageinfo` and Kconfig English text is authoritative. `translations/zh-CN.json` carries curated Applications in all 11 languages (the filename remains for compatibility), while `translations/menu-i18n.json` holds reviewed menu labels. During publish, `i18n-cache.json` reuses existing translations and GitHub Models receives only new or changed text. Quota or service failures retain canonical English, record pending coverage, and never block a successful branch. Advanced menuconfig keeps English visible and exposes the current-locale translation on hover, keyboard focus, or mobile tap. Package names receive layout priority, remain on one line with ellipsis, and expose a localized name tooltip only when that locale has a real translation. The workspace-level `N/M/Y ?` help explains the tristate once: N disables and skips the build, M builds a module or separately installable package that is not included in the firmware by default, and Y enables and builds it into the firmware. One locator searches sources, branches, Targets, arbitrary menu depths, translations, symbols, and usage text.
- Advanced package names create a translation tooltip only when the selected locale has a real translation; they do not fall back to English or expose a bare `PACKAGE_` symbol. A description exposes its full text through one delegated hover handler only when it is visually truncated. After Source and Branch are selected, a spinner occupies the remaining Target columns until the detailed catalog arrives; success replaces it with Target controls and failure exposes a retry action. At runtime the browser follows the Catalog index's exact commit/hash/bytes contract. It fetches the latest index from GitHub Raw first, then tries the pinned shard through jsDelivr, GitHub Raw, and the complete GitHub Release. A candidate is accepted only after compressed-size, SHA-256, gzip, JSON, Catalog-schema-5, relations-schema-2, and shared-engine validation. The failure panel exposes copyable per-provider diagnostics, and retry clears both Cache API data and the in-memory index. The VPS stores no `catalog-data`, and an exact contract can never fall back to an old local shard. Catalog Actions generate those assets; firmware build Actions do not participate in page loading.
- The English UI shows neither translation tooltips nor translation chips. Other desktop locales keep hover/focus help; mobile uses a separate `译/Tr` chip so opening a translation cannot trigger category navigation. Category labels try three 1px reductions before returning to a readable two-line fallback; choices, ordinary options, and package rows keep controls to the right where possible and clamp visible name/description text to two lines, with text inputs allowed to use a second row.
- The browser accepts Catalog data only when schema, commit, compressed byte count, and SHA-256 match the index. New build-request schema 5 also records the Catalog repository, immutable data revision, asset/hash/bytes, Catalog/relations schemas, upstream repository, and upstream source commit. The Issue parser must fetch that exact shard and the Workflow builds that exact upstream commit; schemas 3/4 remain legacy-only. `Top level` remains the root breadcrumb, and curated Applications are UI shortcuts whose validity and dependencies are entirely Catalog-driven.
- Catalog Publish validates each branch independently. A valid branch immediately replaces its rolling shard; a failed or corrupt branch is quarantined and keeps the `catalog-data` last-good result, with the index reporting fresh/stale/unavailable. Partial runs still update rolling data while the failed matrix keeps the workflow red. The complete Release updates only when every branch succeeds and validates.
- Catalog translation uses the workflow's minimal `models: read` permission and processes up to 500 changed texts per weekly run by default. Translation warnings go to `translation-summary.json` and the Publish Summary; manual tables, upstream English, and successfully generated catalogs remain publishable when the model is unavailable.
- Minimal 360T7 configs do not carry the full Kconfig package table. `tools/package-baseline-360t7.json` preserves the complete three-source Developer-search snapshot and `gen-plugins` merges it into `packages.json`.
- Never delete comments inside config files — both the frontend and CI only do line replacement

### 2.5 Build pipeline

- For a Catalog Target, `arch`, `archPackages`, Target/Profile, and Profile-required packages form one atomic build contract. Catalog publishes upstream `Target-Arch` verbatim. The page writes `CONFIG_<arch>`, `CONFIG_ARCH`, and `CONFIG_TARGET_ARCH_PACKAGES`, adds Profile-required packages, and displays both architecture values. Startup order is fixed as Catalog fetch/model → Target/Profile selection → `TARGET_*`/architecture/Target-feature context plus required Profile packages → default theme and minimum-boot presets. The shared engine evaluates dependencies with three standard states: `satisfied`, `unsatisfied` after complete context proves a mismatch, and `deferred` for upstream hidden defaults or Target state that Kconfig/Defconfig has not materialized yet. Interactive and pre-defconfig validation must not reject `deferred` relations or remove Catalog-declared Target/Profile packages, while a known false target condition still fails immediately. Post-defconfig validation treats every remaining `deferred` relation as an error. Recommended presets are rollback-capable UI conveniences: failure restores only the preset snapshot and keeps the loaded Catalog instead of misreporting transport or Catalog-data failure. `parse-request.mjs` uses the same context model; package-specific patches are forbidden in the UI, parser, engine, and Workflow. Never infer build architecture from package architecture or a legacy device table. Defconfig is off by default; when explicitly selected it runs once and is followed by post-defconfig strict validation.

- `.github/workflows/custom-build.yml`: web users build only through Issue attachments; `Smoke All` uses a hidden `repository_dispatch` compatibility trigger, so Actions no longer exposes the legacy manual parameter form. Every upstream `.img.gz` becomes its own Artifact named `request-reference-original-filename`, without a ZIP wrapper; supporting files are grouped as `CONFIG`, `BUILD-LOGS`, `OPTIONAL-PACKAGES`, and `FIRMWARE-OTHER`. Timezone, theme, NTP, and opkg are cross-checked in the submitted config, Summary, `firmware-settings.txt`, and the firmware's `/etc/weig-build-info`. Firmware/config live 30 days; complete logs live 14 days.
- Package-source mirrors are handled automatically by `diy2-generic.sh`: legacy opkg sources rewrite `distfeeds.conf`; APK sources (25.12+) rewrite the build-time `VERSION_REPO`, from which the source generates `distfeeds.list`. Do not treat the generated APK file as a fixed source-tree file.
- Build admission defaults to at most two queued or running builds per requester; a third Issue is commented on and closed. The repository owner is identified from the GitHub login, bypasses that limit, and receives a per-run concurrency group so owner builds do not queue behind one another. A fork can override the positive-integer default through the repository Variable `MAX_BUILDS_PER_USER`. `cancel-build.yml` accepts `/cancel` or `/cancel-build` only from the originating Issue author, tries normal cancellation first, and force-cancels only if it remains active after 15 seconds. Administrators can still manage any run in Actions.
- Root `VERSION` is the shared repository/web minute-level `vYYMMDDHHmm` source; `site-version.json` is its static-deployment copy. Actions records VERSION, the request page version, customizer commit, upstream commit, and all inputs.
- The browser, `parse-request.mjs`, and `validate-catalog-config.mjs` import the same `site/wrt/lib/catalog-engine.js`. It consistently validates Kconfig/packageinfo dependencies, reverse dependencies, choices, selects, implies, conflicts, providers, and hidden residue. Pre-defconfig validation materializes the full Target/Profile context, trusts packages declared by the Catalog target contract, and defers unresolved hidden defaults; post-defconfig removes that trust exemption and rejects every unresolved or unsatisfied relation. Both CI phases report only and never silently rewrite the submitted config. New failures must be represented by Catalog relations, the generic three-state evaluator, or the separate compatibility-rule layer; concrete package-name branches are forbidden in `app.js`, the shared engine, parser, and Workflow. `config/001.presets/config-rules.json` (with its web copy and `tools/config-rules.mjs`) remains a separate temporary layer for semantic choices and empirically verified build compatibility such as ksmbd. The user explicitly deferred migration of this layer into Catalog, so it must not be removed in this change. GitHub opens only after both Catalog-standard resolution and the local compatibility layer complete.
- `config/001.presets/source-build-requirements.json` is the sole source for Source/Branch/Target build requirements; `site/wrt/data/source-build-requirements.json` is only its static web copy. Scope keys are `sources`, `branches`, `systems`, `subtargets`, and `profiles`, with `*` wildcard support; each option declares an exact Kconfig `symbol` and `n/m/y` value. Users may still download an unamended `.config` for editing, but the page must explain and explicitly apply missing requirements before it can download a build-request JSON. `parse-request.mjs` checks the same rules again and rejects omissions before cloning upstream. Add a new requirement only to the authoritative JSON and sync its web copy; never add a separate Workflow or plugin-specific condition.
- For schema 5, the parser fetches the exact Catalog revision/asset/hash/bytes recorded in the request, validates Source/Branch/Target/Profile, architecture, required packages, and all standard relations, then outputs Catalog's `sourceCommit`. The Workflow fetches that commit into a detached HEAD. After optional Defconfig and system overrides, it invokes the same engine again before compilation. Legacy schemas 3/4 retain branch-based compatibility; uncatalogued `custom-target` inputs remain explicit.
- All versioned base configs disable PassWall/SSR Plus/VSSR/TinyProxy and their proxy engines/sub-options by default. `check-all.mjs` fails if any default config contains a proxy `CONFIG_PACKAGE_*=y/m`. Config preflight writes proxy-related symbols selected in the actual pre-build config to `proxy-selected.txt` and the Summary; an explicit user selection may still add its normal dependencies.
- `tools/parse-request.mjs`: full whitelist validation, including device/source/version/variant, packages, login settings, timezone, theme, NTP and opkg. The beginner Issue exposes one required attachment field and recommends the web JSON. The parser still accepts 1–3 GitHub-hosted JSON/`.config`/`config.buildinfo` attachments, but a raw config without web metadata must be loaded on the page first.
- The production Issue path does not call `build-config.mjs`: frontend `applyToConfig()` → complete `build-request.json` → `submitted.config` → `openwrt/.config`. `build-config.mjs` remains only for the hidden internal smoke `repository_dispatch` compatibility path.
- `site/wrt/data/timezones.json` carries the 445-entry OpenWrt LuCI timezone table. With an empty search, the combobox shows about 70 common cities ordered by the current offset from `UTC-12` to `UTC+14`; typing searches all 445 entries. `Beijing` and its Chinese aliases are search-only aliases for `Asia/Shanghai`. On a first visit with no saved choice or imported configuration, the browser-reported IANA timezone is selected; a manual choice is stored locally. The page submits an IANA `zonename`; the parser maps it to the POSIX `timezone`, and all three diy2 scripts write both through `files/etc/uci-defaults/10-weig-timezone`. The control remains 44px high and legacy POSIX values remain accepted.
- The workflow-level `TZ` controls process timestamps only. Do not call `timedatectl set-timezone` on a GitHub-hosted runner: systemd may deny it and fail the dependency-install step. Firmware timezone handling is independent and remains request/diy2 driven.
- `sync-upstream.yml` (weekly, off-peak) refreshes the catalog/seeds and auto-commits; `check-drift.mjs` checks only the shared OpenWrt branch policy and opens an issue on drift; `mirror-upstream.yml` (monthly, needs `secrets.MIRROR_TOKEN`) mirrors upstreams; `smoke-all.yml` triggers a hidden minimal build per source.
- `site-version.yml` watches `site/wrt/**` and `VERSION`, updates root `VERSION` and `site-version.json` together by content fingerprint, then bot-commits them once. Parsers still accept legacy `vYYMMDDHH` requests. Desktop shows the version immediately left of Load configuration, while screens at 560px or below keep it in the right-aligned footer. The actor condition prevents commit loops.

#### Removing builtins with direct-config builds

- In Developer mode, `-id` writes the matching `CONFIG_PACKAGE_*` as an explicit `# ... is not set`; the complete config is used directly unless the request explicitly enables one guarded Defconfig pass.
- `CONFIG_DEFAULT_*` supplies a default value, not a mandatory `select`; it may coexist with an explicit disabled state for the matching `CONFIG_PACKAGE_*`.
- The upstream build system may still resolve symbols selected through Kconfig dependencies; that is distinct from this project explicitly running `make defconfig`. System-baseline entries marked `locked` cannot be removed in the UI.
- Check dependencies and risk warnings before removing a builtin; an explicit disable does not mean the package can never be restored as a dependency.

### 2.7 Deploy & migrate

- Copy the whole `site/wrt/` folder anywhere. Catalog data uses exact cache → latest GitHub Raw index → pinned-commit jsDelivr/GitHub Raw shard → complete GitHub Release; the VPS stores no Catalog, while other static data keeps relative paths and local-first fallback. `OpenWebPage_打开网页.bat` keeps only one visible `wrt-server` window; closing it stops the local preview.
- Browser dynamic imports are fixed at `lib/catalog-engine.js` and `lib/catalog-loader.js`. The `.js` suffix reuses the JavaScript MIME mapping already present on ordinary static servers; `lib/package.json` with `type: module` exists only for Node/CI imports. Legacy `.mjs` files must be removed. The deploy script validates both modules before packaging, after remote extraction, and through a live HTTP MIME/body smoke test after the switch; a missing file, HTML fallback, or non-JavaScript MIME restores the previous site. Archive manifests are checked only by `tools/verify-site-archive.mjs`, which invokes `tar` with `shell: false` and validates all required/forbidden entries in one pass. BAT-level `tar | findstr` pipelines are forbidden, so Unicode/space paths and nested CMD parsing cannot rewrite the command arguments.
- After a fork, edit only `site/wrt/data/project.json` for the main repository, Catalog repository, and blog URL. Runtime links, Issue targets, and Catalog loading follow that file; literal HTML links remain old-deployment fallbacks.
- Blog mirror: `node tools/sync-blog.mjs [blog path]` exact-mirrors the whole `site/wrt/` tree into blog `source/wrt/`, including `.config` files and empty directories. It does not use `fs.cpSync()`; one generic tree walker creates directories, copies files individually, and verifies staging content with chunked SHA-256 before the atomic swap. Unicode/space paths and large binary files use the same path-independent logic. The CLI reports copy progress, failures preserve or restore the previous mirror, and `--check` returns 0 for an exact tree or 3 when synchronization is needed.
- Text-format gate: `node tools/check-text-format.mjs <repository path> --changed` checks only current Git changes and untracked text files. It enforces LF for source/data files, CRLF for BAT/CMD/PowerShell, UTF-8 without BOM, and exactly one final newline according to `.gitattributes`; it reports errors but never rewrites files. The main-repository actions in `Sync_Deploy.bat` run this gate before the full `check-all` and `git diff --check`. Git messages saying CRLF will later be replaced by LF are informational warnings; the actual blocking error is printed separately.

### 2.8 Cloud-build testing guide (manual Run workflow)

**Version and variant must belong to the selected source** — mismatches are rejected instantly by `parse-request.mjs` (the error lists the legal options; just re-run with them):

| source | versions | variants | notes |
|---|---|---|---|
| `ImmortalWrt` | every upstream remote branch | profiles that exist in that branch | old branches without the device are hidden |
| `OpenWrt` | `main` + every `openwrt-*` branch | profiles that exist in that branch | excludes `lede-17.01`, `pcs-standalone-back`, and `master` |
| `lede` | `master` | profiles that exist in that branch | append mode; plugin availability depends on lede feeds |

GitHub's Run-workflow form cannot cascade dropdowns, hence the manual pairing; **the web page never has this problem** (it only offers legal versions/variants per source).

**Recommended test order** after a fresh push or big change: ① use the page to select a currently fresh stable ImmortalWrt branch, a common Target, and `ttyd`; ② verify Advanced hidden-symbol search and a dependency-removal cascade; ③ submit through the Issue path and confirm the pinned Catalog/source commit in Summary; ④ manual `sync-upstream`; ⑤ `smoke-all`; ⑥ then alternate profiles, imported unknown symbols, custom `lanip`, and `@empty`.

**Reading failures**: instant red = parameter validation, so read the `parse-request` step output. Download and compile steps stream raw output live while also writing complete files; if GitHub truncates a long console log, use the `BUILD-LOGS-…` artifact. For compile-stage red, read in order: `00-SUMMARY.txt` → `build-metadata.txt` → `build-diagnostic.log` (if present) → full `download.log` / `build.log` → `errors.txt` / `tail-200.txt` → `package-logs.tar.gz` (if present) → `final.config`. Common causes: `Package xxx is missing`, out-of-space, or a temporary upstream breakage.

**Second-level local checks without waiting for CI**: `node tools/parse-request.mjs`, `node tools/build-config.mjs …` (legacy dispatch compatibility), and `node tools/check-all.mjs` (including every versioned base config in the proxy-default scan).

**Facts**: a build takes ~2–3h uncached; ~20 parallel jobs on the free tier; independent original `.img.gz`, `CONFIG`, `OPTIONAL-PACKAGES`, and `FIRMWARE-OTHER` live 30 days while `BUILD-LOGS` lives 14 days; use a dated tag (e.g. `weige-0727`) to tell batches apart; cancelled issue-builds are commented and closed by the bot too.
