## 1. Overview

- Structure & architecture (overview): see [ARCHITECTURE.md](../ARCHITECTURE.md) (bilingual); **full annotated tree below in §1.1**
- Standard post-change entrypoint: `node tools/dev-assistant.mjs prepare`, which canonicalizes site release bytes, runs a full `site/wrt` text check, stamps VERSION/siteSha, checks changed text, runs `check-all`, `git diff --check`, and prints status; use `node tools/dev-assistant.mjs verify` for a full read-only recheck without restamping
- Web launcher: double-click `OpenWebPage_打开网页.bat`; Local Preview works without configuration, while remote environment URLs come from local `OpenWebPage.local.cmd` and are never stored in source
- Run business generators only when the changed area requires them, and use Local Preview for page self-tests. The production Blog mirror is synchronized from exact `origin/main` only after main promotion; it is not a routine development check
- All generators need only Node.js ≥18, zero npm dependencies

## 2. Where to change what

### 2.1 Look & feel (colors / fonts / breakpoints)

Everything lives in the CSS variables at the top of `site/wrt/app.css`; change once, applies site-wide:
`--bg/--card/--card2` (backgrounds), `--text/--text2/--text3` (text), `--accent*` (brand blue), `--danger/--warn/--ok/--gold` (status), `--radius/--shadow`.
Dark mode is defined **twice** (`html[data-theme="dark"]` for manual and `@media (prefers-color-scheme: dark)` for auto) — edit both. `index.html` and the generated `packages.html` also share a tiny synchronous Theme Bootstrap that runs before the Release Pointer, CSS, and `app.js`: it reads `wrt_theme`, resolves `light` / `dark` / `auto + prefers-color-scheme`, and immediately sets the first-paint background, `color-scheme`, and `theme-color` so dark-mode users never see a white flash. Later theme changes in `app.js` must delegate to the same `__WEIG_APPLY_THEME__` helper instead of duplicating the resolution rule.
Type scale: 17px body (15.5px compact via the Aa toggle); 15px pills/plugin cells/group headers; 14px hints. Breakpoints: 860px / 560px / 400px; plugin grid `repeat(auto-fill, minmax(150px,1fr))` (126px compact).

### 2.2 UI strings & i18n

- Chinese source: `tools/i18n-source.json` (the only hand-edited entry point; keep `{x}` placeholders intact)
- Other 10 languages: `tools/i18n-translations.json` (including Traditional Chinese)
- Then run `node tools/gen-i18n.mjs` → emits `site/wrt/data/i18n.json`
- Validation: all 11 UI languages must be complete; `check-all` rejects any missing entry
- `i18n.json` is network-first and uses localStorage only as an offline fallback, preventing a newly deployed key from being hidden by a stale table for the current page. When a `data-i18n` key is absent, keep the human-readable HTML fallback instead of exposing an internal key.

### 2.3 Plugins

- Curated display metadata: `tools/plugins-meta.json` (name/group/desc/size/hot/locked/warn/per-source `pkgs` mapping/`exclude`). It controls shortcuts and presentation only; dependencies, reverse dependencies, choices, selects, implies, conflicts, and providers come exclusively from the weekly Catalog.
- For 360T7, capacity estimates prefer the median compressed dependency-closure size in `tools/plugin-sizes.json`; missing entries fall back to the hand estimate in `plugins-meta.json`. This snapshot is MT7981-specific, so seed devices always keep hand estimates.
- Group order = the `groups` array order (the proxy group currently sits last)
- Run `node tools/gen-plugins.mjs` afterwards. It warns about packages present in configs but missing from metadata. `data/<device>/packages.json` is still generated for the package reference page and schema-3/4 legacy request compatibility, but the customizer no longer exposes a duplicate raw-package editor.
- Curated names and descriptions live in `tools/plugins-i18n.json`. All ten translated languages, including independent Traditional Chinese, must provide both fields for all 226 plugins; technical package names and `CONFIG_PACKAGE_*` symbols remain unchanged.
- Chinese-only display masking lives in `site/wrt/app.js`: `ZH_SUB` (euphemism replacement) and `EN_MASK` (star masking)

### 2.4 Devices

- Registry: `site/wrt/data/devices.json` (used only by CI, generators, and legacy-request compatibility; the page no longer loads it. Only 360T7 is fully maintained; all other devices are seed configs.)
- Public web data under `site/wrt/data/` must not contain `.config` files. Authoritative base configs live only under `config/`; `gen-plugins.mjs` removes old public copies and generates plugin/package indexes.
- Device catalog: `tools/device-catalog.json`, rebuilt by parsing real `TARGET_DEVICES` and `Device/*` inheritance per branch; `node tools/gen-seed-configs.mjs` then creates an independent minimal config for every source/branch/profile.
- Target controls and plugin options remain schema-driven. `site/wrt/lib/catalog-engine.js` is the only relation calculator; `applyCatalogIntent()` in `app.js` only submits user intent and synchronizes UI state. Enabling an item recursively adds uniquely determined mandatory dependencies and `select` targets. Disabling a dependency recursively disables invalid dependents. Disabling a plugin prunes auto-added dependencies only when no enabled consumer remains and no baseline, recommended, imported, or explicit user layer protects them. Shared and explicitly selected dependencies survive. `imply`, multiple providers, and deferred conditions are left to upstream Kconfig. Plugin-name, translation-package, and theme-link exceptions are forbidden in `app.js`.
- Importing `.config`, JSON, or `config.buildinfo` waits for the matching Catalog before restoring Target/menuconfig state. The page no longer runs a global `proposeRepairs()` pass or silently rewrites imported input. Catalogued symbols continue through the shared interaction engine; truly unknown symbols stay in the import workspace, and the complete uploaded config remains authoritative.
- JSON import starts with strict `JSON.parse`. A legacy WeiG schema 3–6 file may be recovered only when the embedded `config` string has unescaped `.config` quotes and the document also carries the WeiG generated header, `pageVersion`, and `use_defconfig`. Recovery uses fixed field boundaries, never `eval`, and asks the user to export a standards-compliant JSON afterward.
- The Target locator, Current build contract, and build controls share one outer card. On desktop the collapsed header is a strict three-part single row: a narrow locator whose placeholder preserves the discriminating tail as `… Subtarget / Target Profile`, the original collapsible contract header, and an independent control group to the contract frame’s right. `Recommended`, `Configure`, `Defconfig`, `Selected only`, and `Origin` never wrap inside that control group. Expanding the contract reveals its full details across the complete row below. Narrow screens may stack the outer regions responsively, while the control group itself stays single-line. Interactive package changes never dump whole-config violations into a toast; direct package/choice conflicts use a themed N/M/Y switch dialog. The Recommended configuration button remains visible and is disabled, not hidden, while Recommended is off.
- Upstream `.packageinfo` and Kconfig names remain authoritative. Advanced uses one name/symbol search box that indexes the full Kconfig symbol, its `CONFIG_` form, package name, and prompt, including separator-normalized symbol words; searches such as `TARGET_ROOTFS_PARTSIZE`, `CONFIG_TARGET_ROOTFS_PARTSIZE`, `ROOTFS`, and `Root filesystem partition size` therefore resolve to the same option. Long Help/description text is not part of search and the `help` shard is not loaded just for searching. Each row keeps the one-line ID/description layout and fixed N/M/Y controls. IDs, search-result headings, and origin badges use the same primary size as `Advanced menuconfig`, while descriptions are visually secondary. Advanced, immediate-conflict dialogs, and compatibility warnings use one shared selectable-state set for bool/tristate values; states excluded by type, current dependencies, hidden status, or a non-disableable record are not rendered. Native Kconfig promotes an `m` direct-dependency result to `y` for bool symbols, so that case must not reject a valid tristate M. string/int/hex values use a scalar editor with type validation.
- Catalog schema 6 splits each branch into `core`, `graph`, `menu`, `hidden`, `help`, and current-language menu assets. Initial branch selection fetches only `core + graph`; opening Advanced fetches the visible menu and current locale, and the first search adds hidden display metadata. Name/symbol search keeps long Help unloaded and preserves the Advanced lazy-load boundary. `graph` uses compact relations schema 3, while the schema-5 monolith remains a migration fallback. A Worker owns the search index and input is debounced by 180 ms. The Advanced toolbar keeps the complete wrapping breadcrumb on the left and the search field plus fixed `N/M/Y` button (no question mark) on the right; when space is tight the search group moves as a unit to the next line and the path is never truncated. `Selected only` and `Origin` live with Recommended/Configure/Defconfig in the independent single-line control group to the right of the Current build contract frame. Rendering stays bounded to 80-row scroll pages.
- D117 startup-performance contract: the page shell must complete its first paint before the default Catalog autoload begins. During schema-6 `core + graph`, only the symbol/choice indexes needed for Target/Profile defaults may be built; Advanced path, descendant, localized search-text, and Worker indexes stay deferred until the `menu` shard is requested. A valid Catalog Cache API hit reuses the already validated/decoded document, so one asset is never gzip-decompressed or `JSON.parse`d twice. Baseline fixed-point conditional defaults share one validation context per pass, incrementally synchronize ordinary symbols inside that pass, and never override Target-owned context values. `tools/test-catalog-loader.mjs` and `tools/test-catalog-performance.mjs` lock these invariants.
- For Catalog Targets, the action bar shows the current `TARGET_ROOTFS_PARTSIZE` instead of a synthetic RootFS percentage based on legacy plugin size/capacity data. The value opens a guidance dialog with item, current MiB value, and `Target Images → TARGET_ROOTFS_PARTSIZE`, plus a direct Advanced locator. Real `ext4_allocate ... out of space` failures add the same current value/path to `00-SUMMARY.txt`; the page never auto-increases the partition.
- Every ordinary Advanced item can open the unified detail popup whether or not visible text is clipped. English also gets the full CONFIG symbol, English description, and path; other locales add their real translation. Source/Branch loading, exact Catalog commit/hash/bytes validation, schema-6 assets, and the no-Catalog-on-VPS deployment contract are unchanged.
- Desktop uses hover/focus and mobile taps the ID or description; N/M/Y taps only change state. Popup width is constrained by the left edge of the row actions. Category, choice, paging, search Worker, and responsive behavior retain the existing performance design.
- The browser accepts Catalog data only when schema, commit, compressed byte count, and SHA-256 match the index. New build-request schema 5 records the Catalog repository, immutable data revision, legacy asset/hash/bytes, Catalog/relations schemas, upstream repository, and upstream source commit. The Issue parser reads only the fixed index and compares that version contract field by field; it no longer downloads the monolith to scan the complete `.config`. The Workflow builds the exact upstream commit, while schemas 3/4 remain legacy-only. `Top level` remains the root breadcrumb, and curated Applications are browser-Catalog-driven UI shortcuts.
- Catalog Publish validates each branch independently. A valid branch immediately replaces its rolling shard; a failed or corrupt branch is quarantined and keeps the `catalog-data` last-good result, with the index reporting fresh/stale/unavailable. Partial runs still update rolling data while the failed matrix keeps the workflow red. The complete Release updates only when every branch succeeds and validates.
- Catalog translation uses the workflow's minimal `models: read` permission and processes up to 500 changed texts per weekly run by default. Translation warnings go to `translation-summary.json` and the Publish Summary; manual tables, upstream English, and successfully generated catalogs remain publishable when the model is unavailable.
- Minimal 360T7 configs do not carry the full Kconfig package table. `tools/package-baseline-360t7.json` preserves the complete three-source Developer-search snapshot and `gen-plugins` merges it into `packages.json`.
- Never delete comments inside config files — both the frontend and CI only do line replacement

### 2.5 Build pipeline

- **E v2 (production exact-ref routing, accepted):** Phase A passed real dev, slash-branch, stale-commit, and missing-branch Probe routing. Phase B1 then proved with Issue #138 / Run `31280106097` that the real `custom-build.yml` Worker receives `REQUEST_BRANCH=WORKFLOW_BRANCH=dev` with the same full request/workflow commit `63aafb274720345df1d5d659dbdebb2307865dd7`, and a full real OpenWrt backend build finished green. B2/B2.1 make default-branch `build-dispatcher.yml` the single production entrypoint for normal `[build]` Issues, while `custom-build.yml` is a workflow_dispatch-only exact-ref Worker. For opened Issues the Dispatcher freezes the event snapshot, reads the single schema-5 JSON through `REQUEST_EVENT_PATH`, parses only `sourceEnv` + full `requestCommit` + `requestId`, requires branch HEAD to equal that commit, and rechecks state/author/created_at/title/body before dispatching `ref=sourceEnv`. The Worker independently rechecks Workflow branch/SHA, the frozen Issue, exact checkout, and the full parser identity. Staging smoke Issue #139 / Dispatcher Run `31283178862` proved request/workflow/checkout identity at `staging@4ba62ce099f89d6b55a75c2c93fd3f1618b06b9b`; production Issue #140 proved automatic main routing, preserved requester `weigefenxiang`, matched request/workflow branch `main` and commit `4ba62ce099f89d6b55a75c2c93fd3f1618b06b9b`, passed `Verify checked-out commit`, and then successfully exercised `/cancel`. The temporary pre-cutover direct-Issue admission/cancellation compatibility is removed during E closeout; current controls match workflow_dispatch Workers only. The E closeout then completed dev → staging → main and a real `[build]` Issue revalidated admission + `/cancel`; the corresponding Worker was cancelled successfully, so E v2 is CLOSED. Manual `probe` and owner-only `build-canary` remain available. Deployment identity loads `site-version.json` and `build-meta.json` in one fresh release check; Version/siteSha256/branch/full commit must agree or cloud submission stays disabled. The B2.1 quoted Workflow `run-name` YAML-hash gate remains. Worker Actions titles use `requester#Issue request-body`; main uses the request body directly, while non-main uses the normalized branch identity joined with `-`. `run_title` is display-only metadata and must never become an exact-ref routing dependency: during rolling upgrades, a new Worker accepts the field being absent from an old Dispatcher and falls back to the legacy title; a new Dispatcher retries an old Worker without that field only when GitHub returns a 422 explicitly referencing `run_title`; Admission and `/cancel` recognize both workflow_dispatch title shapes. `Verify checked-out commit` prints both `Request commit` and `Checkout HEAD` before asserting equality. F full-site SHA-256 release caching is connected: the pointer is fresh and page/assets/runtime JSON share one siteSha256 cache key.

- For a Catalog Target, `arch`, `archPackages`, Target, and Profile identity remain one atomic build contract. Profile-declared packages move to a compact manager: Follow upstream writes nothing, while explicit Include or Exclude writes `y` or `n`. The submitted config is generically checked only before optional Defconfig. A successful upstream `make defconfig` is not subject to project-specific post-validation. `tools/apply-config-overrides.mjs`, `tools/config-overrides.mjs`, and `system-overrides.json` are removed, so the workflow no longer forces `CONFIG_DEVEL` or `CONFIG_BUILD_LOG`.

- Catalog state keeps baseline, recommended, explicit user, automatic dependency, and imported origin layers. `catalogDependencySymbols` tracks only engine-added values. After disabling a plugin, the engine may prune entries no longer required by any enabled item, while baseline, recommended, imported, and non-`n` explicit user state protect dependencies. Profile package decisions use a sparse `profilePackageOverrides` map that stores only explicit Include/Exclude changes.

- `.github/workflows/custom-build.yml` accepts only web-generated Issue requests. Deployment `build-meta.branch` is source identity: `main` keeps unprefixed Issue/Artifact identity and the Worker title is `requester#Issue request-body`; every non-main request uses its actual branch as the prefix after replacing internal `/` with `_` (for example, `fix/foo` becomes `[build] fix_foo/<request>/...` and `fix_foo-...` Artifacts). The single generic rule lives in `site/wrt/lib/build-identity.js` and is shared by the browser and `parse-request.mjs`; there are no dev/staging/fix/feat or hostname-specific naming branches. `build_ref` remains the stable `<request>-<tag>` build identity, while `artifact_ref` is the environment-aware output name. Request branch/commit and executing Workflow branch/commit are recorded separately in Summary and `build-metadata.txt`. Legacy unprefixed Issues and JSON requests remain accepted.
- Package-source mirrors are handled automatically by `diy2-generic.sh`: legacy opkg sources rewrite `distfeeds.conf`; APK sources (25.12+) rewrite the build-time `VERSION_REPO`, from which the source generates `distfeeds.list`. With `Asia/Shanghai`, the page selects the first Mainland China mirror available for the current Source unless the user has explicitly chosen a mirror; Source changes revalidate that choice. `check-all` combines the device registry and Catalog index and requires every active Source (ImmortalWrt, OpenWrt, lede, and hanwckf) to expose at least one Mainland China mirror. hanwckf reuses the USTC/PKU ImmortalWrt mirror paths. Do not treat the generated APK file as a fixed source-tree file.
- Build admission defaults to at most two queued or running builds per requester; a third Issue is commented on and closed. The repository owner is identified from the GitHub login, bypasses that limit, and receives a per-run concurrency group so owner builds do not queue behind one another. A fork can override the positive-integer default through the repository Variable `MAX_BUILDS_PER_USER`. `cancel-build.yml` accepts `/cancel` or `/cancel-build` only from the originating Issue author, tries normal cancellation first, and force-cancels only if it remains active after 15 seconds. Administrators can still manage any run in Actions.
- Root `VERSION` is the shared repository/web minute-level `vYYMMDDHHmm` code version. `site-version.json` is the Release Pointer and stores that version, the normalized project-input fingerprint, the deterministic raw-byte `siteSha256`, and `hashAlgorithm=sha256`. The SHA recursively covers deployable `site/wrt` bytes and excludes only the self-referential pointer plus deployment-local `build-meta.json`. Prepare first runs `canonicalize-site-release.mjs`, reusing the shared text-format classification to materialize an existing Windows working tree as deterministic `.gitattributes`-defined release bytes, then runs a full `site/wrt` text check before stamping. `.gitattributes` must explicitly classify every published file type as LF/CRLF text or binary; regression covers a stale-CRLF working tree, both `core.autocrlf=false/true`, and a clean detached checkout and requires the same SHA after canonicalization. The SHA algorithm still hashes raw bytes and never normalizes line endings. Use `node tools/site-release.mjs --print` or `--check` for diagnostics. Run Prepare before committing tracked changes; CI uses only `--check`. Promoting the same code from `dev` to `staging` to `main` does not regenerate VERSION. `build-meta.json` supplies per-deployment Commit/Branch/Built/siteSha256 data, and cloud submission requires the same fresh pointer/meta pair with matching version, siteSha256, timezone, branch, and full commit. The page keeps an `MMDDHHmm` compact badge; Actions still records VERSION, request page version, customizer commit, upstream commit, and all inputs.
- Download and parallel compilation use dynamic concurrency; parallel compilation itself enables `BUILD_LOG=1`. On failure, `Shell/collect-build-evidence.sh` freezes the original evidence under `BUILD-LOGS/parallel/`, then `openwrt/logs` is reset before a separate `make -j1 V=s BUILD_LOG=1` retry capped at 180 minutes and stored under `BUILD-LOGS/diagnostic/`. BUILD-LOGS is uploaded even if that retry recovers the build, and `00-SUMMARY.txt` distinguishes FAILED, RECOVERED, and TIMEOUT. The Catalog engine is browser-interaction-only; the backend does not re-judge whole-config package relations. Optional official `make defconfig` remains the only backend configuration resolver; otherwise the submitted config is used directly.
- `config/001.presets/source-build-requirements.json` now carries only the frontend compatibility marker `CONFIG_HAVE_DOT_CONFIG=y`, silently added when Defconfig is disabled; `site/wrt/data/source-build-requirements.json` is the static web copy. The backend does not load this rule and does not reject a request when it is absent. If every build later runs Defconfig unconditionally, this frontend compatibility layer can be removed.
- For schema 5, the parser reads only the fixed Catalog index and verifies the requested revision/legacy metadata plus `sourceCommit`; it no longer downloads the Catalog monolith or scans the complete `.config`. The backend keeps request-safety allowlists and minimal Target/Profile identity only, with no ARCH/ARCH_PACKAGES, package-relation, manual compatibility, theme-package, or build-requirement rejection.
- All versioned base configs disable PassWall/SSR Plus/VSSR/TinyProxy and their proxy engines/sub-options by default. `check-all.mjs` fails if any default config contains a proxy `CONFIG_PACKAGE_*=y/m`. Config preflight writes proxy-related symbols selected in the actual pre-build config to `proxy-selected.txt` and the Summary; an explicit user selection may still add its normal dependencies.
- `tools/parse-request.mjs`: full whitelist validation, including device/source/version/variant, packages, login settings, timezone, theme, NTP and opkg. The beginner Issue exposes one required attachment field and recommends the web JSON. The parser still accepts 1–3 GitHub-hosted JSON/`.config`/`config.buildinfo` attachments, but a raw config without web metadata must be loaded on the page first.
- Issue attachments are the only build entry: frontend `applyToConfig()` → complete `build-request.json` → `submitted.config` → `openwrt/.config`. The old `build-config.mjs`, `repository_dispatch`, and smoke compatibility entry are removed.
- `site/wrt/data/timezones.json` carries the 445-entry OpenWrt LuCI timezone table. With an empty search, the combobox shows about 70 common cities ordered by the current offset from `UTC-12` to `UTC+14`; typing searches all 445 entries. `Beijing` and its Chinese aliases are search-only aliases for `Asia/Shanghai`. On a first visit with no saved choice or imported configuration, the browser-reported IANA timezone is selected; a manual choice is stored locally. The page submits an IANA `zonename`; the parser maps it to the POSIX `timezone`, and all three diy2 scripts write both through `files/etc/uci-defaults/10-weig-timezone`. The control remains 44px high and legacy POSIX values remain accepted.
- The workflow-level `TZ` controls process timestamps only. Do not call `timedatectl set-timezone` on a GitHub-hosted runner: systemd may deny it and fail the dependency-install step. Firmware timezone handling is independent and remains request/diy2 driven.
- `sync-upstream.yml` (weekly, off-peak) refreshes the catalog/seeds and explicitly checks out, commits, and pushes only `dev`. Automatic commits must not use `[skip ci]`, so every generated change enters the same Required CI. `check-drift.mjs` checks only the shared OpenWrt branch policy and opens an issue on drift; `mirror-upstream.yml` (monthly, needs `secrets.MIRROR_TOKEN`) mirrors upstreams. Build regression tests use real web-generated Issue requests rather than a smoke dispatcher.
- `.github/workflows/ci.yml` is the single Required CI with the stable job name `Required CI / 必需检查`. It runs on pushes to every branch and on PRs targeting `dev`/`staging`/`main`, intentionally has no `paths:` filter, and validates VERSION, all repository text files, `check-all`, and changed-line whitespace in that order. It has only `contents: read` and never changes VERSION, commits, or pushes. When local private-maintenance files are absent from a public checkout, `check-all` explicitly skips only private-deployment fixtures while continuing all public contracts; a full local project still runs those private fixtures.

#### Removing builtins with direct-config builds

- In Developer mode, `-id` writes the matching `CONFIG_PACKAGE_*` as an explicit `# ... is not set`; the complete config is used directly unless the request explicitly enables one upstream Defconfig pass. Its output is no longer subjected to a project-specific before/after target-identity comparison.
- `CONFIG_DEFAULT_*` supplies a default value, not a mandatory `select`; it may coexist with an explicit disabled state for the matching `CONFIG_PACKAGE_*`.
- The upstream build system may still resolve symbols selected through Kconfig dependencies; that is distinct from this project explicitly running `make defconfig`. System-baseline entries marked `locked` cannot be removed in the UI.
- Check dependencies and risk warnings before removing a builtin; an explicit disable does not mean the package can never be restored as a dependency.

### 2.7 Deploy & migrate

- Releases use `dev → staging → main`. `Promote_Release.bat` fetches first, validates FF-only ancestry, exact SHA, and VERSION/site-version, then pushes the exact SHA only after an explicit `y`. It fetches again after the push and requires source and target to match the candidate. Enter, `n`, or any other answer cancels without changing refs; force push is forbidden. Promotion does not regenerate VERSION. VPS staging packages must come from exact `origin/staging`, never from the current working tree.
- Protect `staging` and `main` with a GitHub Ruleset that requires the `Required CI / 必需检查` status check, Require linear history, blocks force pushes, and blocks deletion. Keep **Require a pull request before merging disabled**: PRs remain fully available for outside suggestions, but the release pipeline is not forced to manufacture a PR/merge commit before exact-SHA promotion. Accepted external changes should enter `dev`, pass Required CI on that exact SHA, then be promoted to `staging`/`main`.
- `OpenWebPage_打开网页.bat` opens Local, standalone Dev Preview, standalone Staging Preview, VPS Staging, standalone Cloudflare Production, standalone GitHub Pages, Blog Production, or the Staging Preview + VPS pair. Remote URLs live only in a local override file.
- Copy the whole `site/wrt/` folder anywhere. The F Release Contract fetches the release pointer fresh, self-versions the document as `?r=<siteSha256>`, and gives CSS/JS/modules/workers/runtime JSON the same release key. Release-data localStorage is namespaced by siteSha256; old `wrt_cache:*` entries are pruned without clearing user preferences. Ordinary static-data fallbacks use only the current deployment's exact Git commit. Catalog retains its separate pinned integrity contract. `OpenWebPage_打开网页.bat` accepts `0` while Local Preview is running to stop `wrt-server` cleanly and return to the launcher menu; when invoked directly with the `local` argument, it exits after stopping.
- Browser dynamic imports are fixed at `lib/catalog-engine.js`, `lib/catalog-loader.js`, and `lib/catalog-schema6.js`; Advanced search uses `lib/catalog-search-worker.js`. The `.js` suffix reuses the JavaScript MIME mapping already present on ordinary static servers; `lib/package.json` with `type: module` exists only for Node/CI imports. Legacy `.mjs` files must be removed. The deploy script validates all four scripts before packaging, after remote extraction, and through a live HTTP MIME/body smoke test after the switch; a missing file, HTML fallback, or non-JavaScript MIME restores the previous site. Archive manifests are checked only by `tools/verify-site-archive.mjs`, which invokes `tar` with `shell: false` and validates all required/forbidden entries in one pass. BAT-level `tar | findstr` pipelines are forbidden, so Unicode/space paths and nested CMD parsing cannot rewrite the command arguments.
- After a fork, edit only `site/wrt/data/project.json` for the main repository, Catalog repository, and blog URL. Runtime links, Issue targets, and Catalog loading follow that file; literal HTML links remain old-deployment fallbacks.
- Standalone deployment: `site/wrt/` is a first-class static application. For Cloudflare Pages use Production branch=`main`, Preview branches=`dev/staging`, Build command=`node tools/prepare-web-deployment.mjs`, Output=`site/wrt`; GitHub Pages publishes the same directory. Cloudflare must keep query strings in the `/wrt/` cache key (do not Ignore Query String). The pointer uses no-store plus a refresh query, while `?r=<siteSha256>` release assets can be cached long-term. The first pre-F → F production cutover needs a one-time purge or old-HTML TTL wait; later releases do not depend on purges.
- Blog publication mirror: after promotion to `main`, run `node tools/sync-blog.mjs [blog path] --ref origin/main`. The temporary and activated trees are exact-file mirrors and must recompute to the same siteSha256, so any missing/new/changed/deleted file blocks activation. `.wrt-source.json` records Version/Commit/siteSha256; `--check` verifies tree, deployment metadata, and Release SHA. Omitting `--ref` is only for local mirror debugging. The blog does not provide dev/staging previews and must not evolve a second WRT business-code copy.
- Text-format gate: `node tools/check-text-format.mjs <repository path> --changed` checks only current Git changes and untracked text files. It enforces LF for source/data files, CRLF for BAT/CMD/PowerShell, UTF-8 without BOM, and exactly one final newline according to `.gitattributes`; it reports errors but never rewrites files. `tools/dev-assistant.mjs prepare` (invoked by `Sync_Deploy.bat` on Windows) runs canonicalize `site/wrt` → full site text check → stamp → changed-text gate → `check-all` → `git diff --check`; it only prints Git status/suggestions and never runs `git add`, `commit`, or `push`. Git messages saying CRLF will later be replaced by LF are informational warnings; the actual blocking error is printed separately.

### 2.8 Cloud-build testing guide (manual Run workflow)

**Version and variant must belong to the selected source** — mismatches are rejected instantly by `parse-request.mjs` (the error lists the legal options; just re-run with them):

| source | versions | variants | notes |
|---|---|---|---|
| `ImmortalWrt` | every upstream remote branch | profiles that exist in that branch | old branches without the device are hidden |
| `OpenWrt` | `main` + every `openwrt-*` branch | profiles that exist in that branch | excludes `lede-17.01`, `pcs-standalone-back`, and `master` |
| `lede` | `master` | profiles that exist in that branch | append mode; plugin availability depends on lede feeds |

GitHub's Run-workflow form cannot cascade dropdowns, hence the manual pairing; **the web page never has this problem** (it only offers legal versions/variants per source).

**Recommended test order** after a fresh push or big change: ① use the page to select a currently fresh stable ImmortalWrt branch, a common Target, and `ttyd`; ② verify Advanced hidden-symbol search and a dependency-removal cascade; ③ submit through the Issue path and confirm the pinned Catalog/source commit in Summary; ④ manual `sync-upstream`; ⑤ submit real Issue requests for the other source/Target combinations; ⑥ then alternate profiles, imported unknown symbols, custom `lanip`, and `@empty`.

**Reading failures**: instant red = parameter validation, so read the `parse-request` step output. Download and compile steps stream raw output live while also writing complete files; if GitHub truncates a long console log, use the `BUILD-LOGS-…` artifact. For a parallel failure (including one later recovered by `-j1`), read `00-SUMMARY.txt` → `build-metadata.txt` → `parallel/errors.txt` / `last-targets.txt` / `tail.txt` / `build.log` / optional `package-logs.tar.gz` → the corresponding files under `diagnostic/` → `download.log` → `final.config`. Parallel and diagnostic package logs are frozen separately and never overwrite each other. Common causes include missing packages, out-of-space, or temporary upstream breakage.

**Second-level local checks without waiting for CI**: run `node tools/parse-request.mjs` with `REQUEST_FILE` or `REQUEST_MANIFEST` pointing to a web-generated attachment, then run `node tools/check-all.mjs` (including every versioned base config in the proxy-default scan).

**Facts**: a build takes ~2–3h uncached; ~20 parallel jobs on the free tier; independent original `.img.gz`, `CONFIG`, `OPTIONAL-PACKAGES`, and `FIRMWARE-OTHER` live 30 days while `BUILD-LOGS` lives 14 days; use a dated tag (e.g. `weige-0727`) to tell batches apart; cancelled issue-builds are commented and closed by the bot too.

## D100: Catalog Schema 6 vs. the Actions build contract

Every Catalog branch index must explicitly contain:

```json
{
  "assets": { "core": {}, "graph": {} },
  "legacy": {
    "asset": "source--branch.json.gz",
    "hash": "<compressed sha256>",
    "bytes": 123,
    "catalogSchema": 5,
    "relationsSchema": 2
  }
}
```

`assets` serves the browser's Schema 6 / Relations 3 runtime. `legacy` serves the exact Schema 5 / Relations 2 asset validated by Actions. Contract changes must be reviewed together in `site/wrt/app.js`, `site/wrt/lib/catalog-loader.js`, and `tools/parse-request.mjs`. Never combine `branch.asset/hash/bytes` with schemas taken from the in-memory `MENU_CATALOG`. A branch without an explicit `legacy` contract may still be browsed, but cloud-build submission must be blocked.

## Catalog compatibility evidence rules

A small number of compatibility facts that upstream Kconfig/Catalog cannot yet express, but real builds have confirmed, live in `compatibility.json` at the root of `WeiG-OpenWrt-Menuconfig-Catalog` and are published as one `compatibility.json.gz`. This is not a second dependency database. Before adding a rule or field, inspect Kconfig, Catalog relations/index, the browser runtime model, and the request contract. Existing symbols, types, N/M/Y capabilities, names, dependencies, providers, conflicts, and hashes must be referenced through package/rule IDs and never copied.

- Channels are fixed one-to-one: AutoBuild `fix/* → catalog-fix`, `dev → catalog-dev`, `staging → catalog-staging`, and `main → catalog-data`. `site/wrt/data/project.json` owns the mapping. Preview channels neither read nor create the production Release or a Pages URL.
- Eighteen seconds after a Catalog load succeeds, the browser prefetches the global compressed rules at low priority. An unchanged compressed SHA reuses memory and then the Cache API without another download. Actual request creation must obtain and validate the rules; missing or corrupt rules cannot be bypassed with Force.
- Evidence rules run only during One-click self test and actual `build-request.json` creation. An ownership rule describes files installed into the firmware, so it triggers only when every participant is `y`; `m` builds a package without treating its payload as installed in the image. The modal places “Conflicting file / rule and evidence” and “Recommended plan / estimated changes” in two wrapping, right-aligned information rows; paths and the recommended action remain on their following lines, and every value comes from the active rule and plan. It offers three actions: “Recommended plan” applies the unique lowest-cost plan derived by the shared Catalog engine, N/M/Y can be chosen inside the dialog from existing Catalog records, or the current state can be kept and forced. A successful recommendation keeps the dialog open, refreshes the actual states, and continues only after the user closes it; a failed application rolls back in place. The action bar groups “Force, Custom | Close, Recommended” and preserves that order in a two-by-two mobile grid. Package IDs share Advanced's responsive title-size variable, while full explanatory text uses one derived shared size with a 14px floor. Equal-cost plans disable the recommendation and explain why. The first Force click only opens a risk-confirmation view; Back or its close icon returns to the original choices with N/M/Y preserved, and only the second “Confirm and force” click produces the forced audit.
- Bool/tristate `default` values and conditions are evaluated in declaration order by the shared Catalog engine. The Catalog model derives a closed-world boundary from existing expressions: a missing symbol referenced only by a default, absent from records, and outside Target/dependency context evaluates as `n` so fallback can continue; genuinely omitted context remains deferred and must not be skipped. Top-level `if` splitting is quote-, escape-, and parenthesis-aware so string literals are never mistaken for conditions. An `m` result for either a bool default or its direct dependency normalizes to `y`, matching native Kconfig semantics. The browser renders and serializes only the N/M/Y values allowed by the shared engine in the current context, so raw expressions and illegal values can never become button labels. String (including literal `"n"` and `"use if available"`), int, and hex defaults retain their literal semantics.
- A force acknowledgement is memory-only and binds the rule SHA, data channel, Source/Branch, `catalogStateRevision`, and triggered rule IDs. Submission does not ask again after an unchanged self test; any configuration, Source/Branch, rule-SHA, or page-state change invalidates the acknowledgement.
- The build backend only normalizes and records forced rule IDs plus rule SHA/Source/Branch audit data. It does not re-evaluate compatibility, lock packages, or change `.config`. Existing immediate Kconfig/Catalog hard conflicts remain unchanged.
- Compatibility work starts on `fix/catalog-compatibility` in both repositories, with Catalog data published to `catalog-fix`. Promotion through `fix → dev → staging` requires an explicit user decision after the CDN-hosted page passes testing; `main/catalog-data` stays frozen before that validation.

The Catalog repository documents rule fields and evidence lifecycle separately in `docs/COMPATIBILITY.md` and `docs/COMPATIBILITY.en.md`.
