**Онлайн-конфигуратор + облачная сборка** прошивок OpenWrt. Выберите на веб-странице исходный код, версию и плагины — GitHub Actions скомпилирует всё автоматически, а готовую прошивку можно бесплатно скачать.

На данный момент **360T7 (MT7981)** — полностью поддерживаемая модель; остальные 200+ моделей на странице открыты в **seed-режиме** (гарантируется лишь уровень «устройство загружается», без проверки на реальном железе — на ваш страх и риск; как перевести модель в разряд полностью поддерживаемых, см. ниже в разделе для мейнтейнеров).

- **Ветки версий**: индексируются все удалённые ветки ImmortalWrt. Для OpenWrt включены `main` и все ветки `openwrt-*`, кроме `lede-17.01`, `pcs-standalone-back` и `master`. Страница создаёт отдельную конфигурацию для каждого источника, ветки и профиля устройства и показывает только реально существующие upstream-комбинации.
- Интерфейс поддерживает **11 языков** (упрощённый китайский / традиционный китайский / английский / русский / испанский / португальский / японский / корейский / немецкий / французский / вьетнамский), автоматически подстраивается под язык браузера, в правом верхнем углу его можно переключить вручную; при отсутствии перевода автоматически используется английский

## Я пользователь: как заказать свою прошивку

1. Откройте страницу, выберите **Source → Branch → Target System → Subtarget → Target Profile → плагины** и укажите идентификатор сборки.
2. Нажмите **Отправить облачную сборку → Скачать запрос и открыть GitHub**. Загрузите только что созданный `build-request.json` и нажмите **Create**; вводить устройство, исходник, версию и раздел не нужно. Готовый `.config` или `config.buildinfo` сначала загрузите на веб-странице для определения устройства.
3. Бот ответит в Issue ссылкой на текущую сборку; полная компиляция занимает примерно **2–3 часа**.
4. После завершения сборки бот уведомит вас комментарием; откройте страницу сборки и скачайте файлы внизу, в разделе **Artifacts**:
   - `время-исходное-имя.img.gz`: каждый финальный образ напрямую и без ZIP; для первой установки обычно нужен `factory`;
   - `время-CONFIG`: отправленный/фактический конфиг и метаданные;
   - `время-BUILD-LOGS`: полные журналы и ошибки, хранятся 14 дней;
   - `время-OPTIONAL-PACKAGES` / `время-FIRMWARE-OTHER`: пакеты M и вспомогательные файлы.
5. Если сборка не нужна, выберите **Отправить облачную сборку → Только скачать .config**. Actions выполняет `make defconfig` только при явном включении **Defconfig**; иначе полный `.config` остаётся главным входом. Без Defconfig страница незаметно добавляет `CONFIG_HAVE_DOT_CONFIG=y`; backend не отклоняет запрос из-за этого флага или собственной проверки зависимостей.
6. Страница загружает `build-request.json`, `.config` и `config.buildinfo`. Доступен поиск по полному списку IANA OpenWrt/LuCI в формате `(UTC±HH:MM) Region/City`, а также выбор темы LuCI, NTP и **зеркала пакетов (APK / OPKG)**. Часовые пояса материкового Китая используют автоматическую цепочку USTC → PKU → источник; в других регионах сохраняется источник, а сбой зеркала не останавливает сборку.

> 💡 После прошивки: откройте в браузере **192.168.1.1** (или адрес, заданный вами на странице отправки), имя пользователя **root**; **пароль пустой** (установите его сразу при первом входе) — и только у источника Lean LEDE начальный пароль `password`.
>
> 💡 В правом верхнем углу страницы есть кнопка **Самопроверка**: одним нажатием проверяются доступность источников данных (три уровня: локальный / jsDelivr / raw), логика генерации .config и связь с GitHub. При проблемах с загрузкой сначала нажмите её для диагностики.
>
> 💡 При выборе плагина с зависимостями (например, помощника маршрутизации трафика MWAN3) необходимые плагины отмечаются автоматически; зависимости уровня ядра и библиотек дополняются автоматически при компиляции — об этом можно не беспокоиться.
>
> ⚠️ Для скачивания Artifacts необходимо войти в GitHub. Прошивка, конфигурация и сведения о сборке хранятся 30 дней; `BUILD-LOGS` — 14 дней.
>
> ⚠️ Перепрошивка сопряжена с риском. Вариант **с большим разделом 108M** требует уже установленного «неубиваемого» U-Boot (ubootmod); вариант **с заводской разметкой** прошивается напрямую без изменения разделов, но места в нём мало — если отметить слишком много плагинов, сборка завершится ошибкой или прошивка не поместится.

### Как найти свою прошивку в Actions

Сборки в списке именуются по шаблону `Build 定制 · 你的标识 · 源码 版本/变体` — просто ищите указанный вами идентификатор: репозиторий → **Actions** → **custom-build**.

## Самостоятельная сборка через Fork

Если вы не хотите стоять в очереди в общем репозитории или хотите изменить конфигурацию по умолчанию, всё можно сделать полностью самостоятельно:

1. Нажмите **Fork** в правом верхнем углу, чтобы скопировать этот репозиторий в свой аккаунт;
2. В своём Fork откройте **Settings → Features и включите Issues**, затем на странице **Actions нажмите зелёную кнопку, чтобы включить workflows**;
3. Вернитесь на страницу конфигуратора, на шаге ④ выберите **Мой собственный Fork** и укажите своё имя пользователя GitHub — после этого сборки будут выполняться в рамках вашей собственной бесплатной квоты;
4. Страница скачает `build-request.json` и откроет Issue с единственным обязательным полем вложения. Загрузите файл и отправьте форму; Actions использует вложенный полный `.config`, не пересоздавая его из base config репозитория.

## Я мейнтейнер: как добавить плагин / изменить конфигурацию

Поток данных: `config/<бренд>/<модель>/*.config` сохраняется для импорта старых конфигураций и исторических запросов (для 360T7 сейчас имеется 14 конфигураций источник/ветка/Profile). Новые параметры сборки динамически поступают из `WeiG-OpenWrt-Menuconfig-Catalog`; окончательным входом каждой Issue-сборки служит полный `.config`, экспортированный в `build-request.json`.

### Добавление нового плагина в список

1. Убедитесь, что во всех четырёх base-конфигурациях уже есть строка `# CONFIG_PACKAGE_luci-app-xxx is not set` для этого пакета (если её нет, значит пакета нет в feeds данного источника — сначала добавьте feed в diy-скрипте и обновите base-конфигурацию);
2. Добавьте запись в массив `plugins` файла `tools/plugins-meta.json`: `{ "id": "xxx", "name": "название", "group": "группа", "desc": "описание одной фразой", "size": 2, "hot": false }` (если имя пакета не совпадает с суффиксом после `luci-app-` или различается между тремя источниками, добавьте поле `pkgs` для явного сопоставления; если у плагина есть обязательные плагины уровня luci-app, добавьте `requires: ["id-зависимости"]` — страница автоматически отметит их при выборе);
3. Запустите `node tools/gen-plugins.mjs` — скрипт заново сгенерирует `site/wrt/data/360t7/plugins.json`, сохранит авторитетные base-конфигурации только в `config/` и выдаст предупреждения о плагинах, которые «есть в конфигурации, но не включены в список»;
4. Сделайте commit и push. Менять код страницы не нужно — новый пункт появится автоматически.

### Включение / добавление модели роутера

Каталог моделей находится в `site/wrt/data/devices.json` и организован по брендам; 360T7 относится к полностью поддерживаемому уровню, остальные модели работают в **seed-режиме** (sources генерируются из шаблона, используется общая seed-таблица плагинов, гарантируется только загрузка устройства). Шаги перевода seed-модели на полностью поддерживаемый уровень:

1. Найдите модель в `devices.json` и заполните `sources` в соответствии с реальной ситуацией (имя config-файла для каждого источника, ветки versions, варианты variants и пары замены разделов);
2. Поместите base-конфигурации каждого источника в `config/<бренд>/<id-модели>/`, соглашение об именовании — `<бренд>_<модель>_<источник>.config` (для большинства моделей в репозитории уже сгенерированы «минимально загружающиеся» seed-конфигурации, содержащие только целевую модель + LuCI; их можно использовать как есть или дополнять поверх);
3. Запустите `node tools/gen-plugins.mjs` (для каждой включённой модели будет сгенерирован собственный plugins.json);
4. Дымовой тест: запустите по одной облачной сборке для каждого источника и убедитесь, что образ успешно собирается.

Код страницы и workflow менять не нужно — параметр `device`, как и прежде, проверяется по белому списку.

### Безопасность

- Issue принимает 1–3 вложения GitHub и распознаёт `build-request.json`, `.config`, `config.buildinfo`; проверяются поля, разрешённые значения, размер, контракт источника и минимальная идентичность Target/Profile. Полный конфиг является главным входом. Официальный `make defconfig` запускается один раз только при явном Defconfig; backend не перепроверяет зависимости, производные поля архитектуры, состояние темы и собственные требования сборки.
- идентификатор сборки (tag) очищается до китайских и латинских символов, цифр и дефисов и используется только для именования artifact и отображения;
- права workflow сведены к `contents: read + issues: write`.
